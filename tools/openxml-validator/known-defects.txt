# Open XML validity findings that are the Excel backend's and cannot be fixed
# from here. `.github/scripts/validate-xlsx.sh` compares a run's findings
# against this file: anything not listed fails, and so does anything listed
# that has stopped happening — a waiver nobody has to remove is a waiver that
# outlives its reason.
#
# Everything below `#` is data and must match the validator's output exactly.
# Comment lines and blank lines are stripped before the comparison.
#
# A workbook is named here by its basename, which is why the script refuses a
# run whose inputs share one: a waiver written for `examples/shapes.yxl.yaml`
# would otherwise cover `tests/validity/shapes.yxl.yaml` without saying so.
# Both corpora are ours to name, so a collision is always a rename away.
#
# ---------------------------------------------------------------------------
# modular.xlsx — a table-backed slicer's cache writes `ext` in the wrong
# namespace. `write_slicer_cache_xml_table` (mbtexcel `xlsx/slicer.mbt`) makes
# the x14 namespace the part's default and then writes a bare `<ext>`, which
# therefore lands in x14; `CT_SlicerCacheDefinition`'s `extLst` is typed
# `x:CT_ExtensionList`, so the child has to be `x:ext`. The `x` prefix is
# already declared on the root element, so upstream's fix is the prefix.
# The pivot-backed path is unaffected — there the part's default namespace *is*
# the main one, so its bare `<ext>` is already right, which is why the
# backend's own demos do not show this.
# Not reported upstream yet — see ROADMAP §9, which also records why waiving
# it beats the alternative of refusing table slicers.
modular.xlsx
  Sch_InvalidElementContentExpectingComplex /x14:slicerCacheDefinition[1]/x14:extLst[1]
    The element has invalid child element 'http://schemas.microsoft.com/office/spreadsheetml/2009/9/main:ext'. List of possible elements expected: <http://schemas.openxmlformats.org/spreadsheetml/2006/main:ext>.

# ---------------------------------------------------------------------------
# conditional-dxf-order.xlsx — a `<dxf>`'s children are written in the order
# `numFmt, font, fill, border, alignment`, while CT_Dxf (ECMA-376 §18.8.14) is
# the sequence `font, numFmt, fill, alignment, border, protection`. Excel does
# not merely ignore the part: `styles.xml` is load-bearing, so it reports the
# workbook as damaged and repair *discards styles.xml whole* — every fill,
# border, font and number format in the workbook, not only the conditional
# format that produced the `<dxf>`.
#
# A `<dxf>` carrying only a font and a fill comes out in a legal order by
# accident, which is why `conditional.yxl.yaml` — twenty-four rules — never
# showed it: no style there has a `format:` or an `align:`. That corpus file
# stays clean and keeps proving the feature validates; this one exists solely
# to hold the defect still until upstream fixes it.
#
# Reported as office.mbt#531. Downstream: t-ujiie-g/yxl#81, which is where the
# blast radius is written down. See also ROADMAP §9.
conditional-dxf-order.xlsx
  Sch_UnexpectedElementContentExpectingComplex /x:styleSheet[1]/x:dxfs[1]/x:dxf[1]
    The element has unexpected child element 'http://schemas.openxmlformats.org/spreadsheetml/2006/main:font'.
